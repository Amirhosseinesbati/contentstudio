# Security and data handling

ContentStudio is designed for one customer per installation. The seeded demo has two isolated workspaces to exercise boundaries. Human users have admin, operator, or viewer roles; passwords use Argon2 hashes and opaque session tokens are stored by hash. Login has bounded local per-peer/account failure counts before Argon2 verification; use an additional public reverse-proxy limit when running multiple API workers. Cookies are HTTP-only and SameSite Strict. Browser writes to `/api/v1/` reject cross-site and sibling-site Fetch Metadata; when that header is absent they require a matching `Origin` in CONNECTED mode. The `/internal/` service-token API is separate. The web proxies preserve the public Host for origin checks. Set secure cookies and TLS for deployment. n8n calls the internal API with a server-only service token; the browser never receives n8n credentials, WordPress passwords, or raw webhook resume URLs.

Every business row carries a workspace ID. API handlers scope source, segment, batch, claim, asset, review, job, draft, calendar, package, and media access through that workspace. Direct object IDs do not grant access. Source and render file routes resolve paths under the signed-in workspace and reject path escape. Uploads require a rights attestation, inspect file signatures for supported audio/video formats, and enforce a configurable byte limit. The render service accepts typed slide fields and validated clip ranges and passes an argument list to FFmpeg; it never executes model-generated shell text or scripts.

Quotes must appear verbatim in cited transcript spans, displayed numeric tokens need cited evidence, and prohibited brand phrases create warnings. Approval is blocked while warnings remain and is bound to the exact current content hash. These deterministic checks do **not** establish contextual truth. A reviewer must inspect qualifications, negation, speaker identity, rights, and clip boundaries. Transcript corrections create a new version and stale only dependent approvals/claims. Model and document output is treated as untrusted content.

The local simulator uses fictional reserved addresses and does not contact real recipients. Connected mode needs a customer-owned HTTPS WordPress URL and a scoped application password. Avoid arbitrary user-supplied URL fetching; connector destinations should be configured/allowlisted. n8n workflow JSON exports contain no secrets. Store `.env` and provider credentials in a secret manager or protected deployment configuration, not Git or screenshots. Back up n8n's encryption key separately; without it restored credentials cannot be decrypted.

## Deployment gaps to close

- Perform a customer threat review of the origin policy, reverse proxy, TLS, cookie domain, password reset/invitation, and account revocation. Local demo accounts/passwords must be replaced. Rate-limit login at the public reverse proxy in addition to the API's local throttle.
- Define and test retention/redaction for raw media, transcript corrections, exports, logs, model traces, and backups. The current pilot does not claim an automated deletion sweep.
- Restrict network egress and n8n admin access; replace internal demo task runner for connected operation as documented by n8n.
- The local n8n replay verified actual triggers, duplicate preservation, conflict/malformed Error Trigger runs, and one simulated 429 retry with a single resulting draft. Still test restart, concurrent generation/dispatch, ambiguous provider timeouts, and full database/media/n8n-key restore. The completed 243,539-byte ContentStudio dump restore checked 14 table counts only. Docker later degraded with virtual-disk I/O errors and API 500; current runtime health is unverified.
- Review the actual model/transcription provider data terms and consent/rights for every customer source. No real customer data was used in this build.

These are release requirements. A passing local fixture suite is not a security audit.
